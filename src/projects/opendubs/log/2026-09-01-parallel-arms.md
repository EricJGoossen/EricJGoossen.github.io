A plan for two arms is only collision-free if both arms run it at the same time. On real hardware, though, a multi-arm plan was sent one arm at a time: the second arm's trajectory started when the first one finished. That doubles the time, and it walks the arms through states the planner never checked. Run that way, the crossing plan from the ArmGroup entry puts the arms through each other in 97 of 1,400 checked states. I rewrote execution so every arm's trajectory is sent from its own thread with **one shared start stamp**, 0.15 s in the future, so the controllers begin on the same tick; if any arm fails or is aborted, the others are cancelled with it.
{% endrow %}

Running arms in parallel exposed two concurrency bugs. Each hardware context had been spinning ROS's process-wide executor, which can't be spun from two threads at once, so each now spins its own. And the simulated "shadow" copy of the robot, kept in step with the real arms for collision checking, was being updated from both arms' threads at once, which crashed the process on the robot. A lock around every update of that shared MuJoCo state fixed it. To bring all of this up safely, I wrote an eight-stage, operator-gated hardware validation suite, from CAN bring-up, e-stop checks, sensor accuracy and URDF consistency through first activation, open-loop motion, trajectory execution, aborts, both arms moving independently and together, and an extended soak test. A person confirms every real motion before it's sent, by typing a phrase for the dangerous ones, and a capability only counts as working after several passes in a row.
